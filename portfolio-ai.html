01AI Agent 飞书智能助手
2026.03 – 2026.05 ｜ 独立完成 ｜ github.com/xiaoyun1123/feishu-agent-bot

基于开源 Agent 框架（约 3K stars）完成飞书生态产品化——把只能在终端里敲命令的 AI Agent，改造成用聊天就能指挥的助手。

问题
开源 CLI 框架能力很强，但每次使用都要开终端、记命令、手动传路径。真正阻碍它的不是能力，是使用成本。
判断
应该把交互层搬到用户已经在用的地方，而不是要求用户去适应工具。飞书是我每天打开几十次的软件，所以产品形态定为"在飞书里发一句话"。
关键决策
  • 三层架构：飞书表现层 → Agent 调度层 → 工具执行层。分层的目的是让"改交互不影响执行、换工具不重写交互"。
  • 9 个原子工具的能力边界：明确哪些自动执行（读取、截图）、哪些必须人工确认（写文件、执行代码）、哪些直接禁止。边界本身就是产品决策。
  • 21 条危险命令过滤规则：覆盖文件删除、注册表修改、磁盘格式化、进程终止、系统目录写入 5 类，命中即拦截并转人工，不可绕过——在自主性与可控性之间划硬线。
  • 自进化技能系统：Agent 每完成一类新任务，执行路径自动结晶为可复用技能模板，累计 10+ 项，形成"用得越久越好用"的飞轮。
  • 上下文窗口策略：28,000 chars 预算，最近 8 轮完整保留 + 更早对话摘要压缩，在连贯性与 token 成本之间取平衡。
  • 卡片渲染的物理限制：飞书 Markdown 表格在 10–20 行会截断，超限自动折叠，而不是让用户看到半张表。
结果
V1.0 → V2.0 修复 5 个关键问题（空页面崩溃、错误无限重试、上下文裁剪导致 API 400、状态泄漏、多实例连接竞争），守护进程连续运行 2+ 月零宕机。

02Chrome 智能填表扩展 v1.2.1
2026.05 ｜ 独立完成 ｜ github.com/xiaoyun1123/auto-fill-extension

面向求职场景的浏览器扩展，自动识别各招聘平台的表单字段并填充简历信息。起点很简单：我自己每天填十几张表，太烦了。

问题
招聘平台的表单结构各不相同，字段命名五花八门。真正的问题不是"能不能识别"，而是识别错了怎么办——填错一个手机号比不填更糟。
关键决策
  • 5 级渐进匹配引擎：CSS 选择器精确匹配（300 分）→ 属性匹配 → 标签匹配 → 中文子串模糊匹配（长度加权）。每一级的阈值和权重都是在"填得准"和"填得上"之间做取舍，纯规则覆盖约 85%。
  • LLM 只兜底长尾：规则处理确定性场景（快、零成本），LLM 语义映射只在前 4 级都失配时触发——把付费调用压到只在必要处发生，这是覆盖率与成本的 tradeoff。
  • Answer Memory：用户手动修正某字段后自动记录，下次同类字段直接复用修正值，减少 LLM 调用，也让工具随着使用变准。
  • 技术约束转产品方案：React/Angular 的受控组件会让直接写入的值"弹回"，通过原生 setter + dispatchEvent（composed:true）绕过虚拟 DOM，让框架站点的填充成功率与原生站点持平。
结果
适配 9 个主流招聘平台（含 Workday、Greenhouse、Lever 等海外站点），中文招聘平台覆盖率 >90%。

03多平台 UGC 情感监控平台
2026.04 ｜ 独立完成 ｜ github.com/xiaoyun1123/ugc-sentiment-monitor

集采集、AI 分析、可视化于一体的舆情工具，用于品牌口碑监测与竞品声量对比。

问题
要判断一个品牌或产品在社交平台上的真实口碑，只能人工一条条翻；翻完也说不清"整体是正还是负"。
判断
情感分类做到"正/负/中性"三级就够用，因此选择调用现成大模型而不是自训练模型——零标注成本、迭代更快。在精度已经够用的场景，多花三个月训练模型是过度设计。
关键决策
  • 补"热榜"模式：最初只做关键词搜索，实际用起来发现大量热门内容根本不含目标关键词。热榜追踪是针对这个真实盲区补的功能。
  • 每平台独立解析器：三个平台响应格式完全不同，不做"通用解析"，各写各的，出问题好定位。
  • 优雅降级：单平台失败不影响其他平台；LLM 调用失败降级为 unknown 而不是让整批任务崩掉。
结果
单次任务 30 秒内完成三平台抓取与分析，累计数千条结构化样本；Streamlit 交互看板支持情感占比、日度趋势、高频词云、头部内容排行，可按平台与日期动态筛选。

04MCP Server 矩阵（4 个）
2026.04 – 2026.05 ｜ 独立完成 ｜ github.com/xiaoyun1123/mcp-servers

用 MCP（Model Context Protocol）把 Zotero、Obsidian、Stata、Blender 四个异构系统的能力，封装成 AI Agent 可以直接调用的标准接口，共 180+ 个工具。

问题
大模型知道"该怎么分析"，但它接触不到我的文献库、笔记库和统计软件。模型能力与私有数据之间缺一层标准化的接口。
关键决策
  • 工具粒度：每个 Server 不暴露底层全量能力，而是挑出高频、语义明确的动作封装成工具。工具太多模型会选错，太少又不够用。
  • 破坏性操作防护：Stata Server 对可能覆盖数据、删除文件的命令做自动检测拦截，防止模型"好心办坏事"。
  • Blender 的双向 TCP 架构：Python 侧与 Blender Addon 侧各自维护状态，覆盖建模、材质、动画、物理仿真、渲染全流程。
结果
四个 Server 支撑了我自己的论文写作、知识管理、建模工作流；对 MCP 协议的工具发现、权限模型、上下文注入机制有实操层面的理解。

05个人知识库系统 Claudian
2026.03 – 2026.05 ｜ 独立设计

基于 LLM 的个人知识管理系统，核心主张是"编译而非检索"——数据进入时一次性加工成结构化知识，后续复用时不再重复计算。

问题
读过的论文、看过的视频、存下的网页散落在各个地方，要用的时候找不到；就算找到，也要重新读一遍才知道它讲了什么。
判断
传统 RAG 每次提问都要重新检索、重新理解，同一份材料被反复"读"很多遍。如果把理解发生在入口而不是出口，成本只付一次，之后每次复用都是零边际成本。
关键决策
  • 多模态入口统一：视频转录、PDF 提取、网页抓取、图片描述四种素材入口，统一落成结构化 Markdown，下游不必关心来源。
  • LLM 编译引擎：自动提取概念、人物、方法论、矛盾关系，按语义写入知识图谱三类节点。
  • 质量维护自动化：定期检测断链、孤儿页面、过期内容、索引漂移、矛盾未更新 5 类问题——知识库不维护就会腐烂。
结果
累计处理素材 200+ 条；系统已连续使用数月，成为我做研究、写材料的主要工作入口。

06A 股智能选股与量化风控系统
2026.04 – 2026.05 ｜ 独立完成

基于多 Agent 协作的 A 股分析系统，把"全市场 5,500+ 只股票"从不可能交给 LLM 处理的规模，压到 LLM 只处理真正需要判断的部分。

问题
让大模型逐只分析全市场股票，成本和时间都无法承受。但粗暴降采样又会漏掉机会。
关键决策
  • 三级漏斗：0 级纯规则 15 秒筛掉约 99% 无效标的 → 1 级 LLM 做主题判断筛至 1–3 个板块 → 2 级四 Agent 并行深挖。把 LLM 用在"需要判断"的环节，而不是"能算出来"的环节。
  • 多因子加权：技术面 30% + 基本面 25% + 情绪面 25% + 板块对齐 20%，每只标的输出 0–100 评分、操作建议、目标价位与风险等级。
  • 风控优先于收益：日亏损 3% 熔断、单只仓位 20% 上限、总持仓 5 只、T+1 规则，外加 LLM 熔断器（连续失败 3 次断开 60 秒后试探恢复）。
  • 数据源三层容灾：每个数据点配主/备/兜底三个来源，单一数据源失效时系统降级运行而非崩溃。
结果
全市场分析从 46 小时压缩到分钟级；系统在多个数据源先后失效的情况下持续可用。

08AI 在真实组织中的落地（非个人项目）
2025.07 – 至今 ｜ 西藏民企课题 / 极米科技

自己做出工具只是第一步，让别人愿意用才是难点。这两段经历回答的是同一个问题：怎么在一个并不天然拥抱新技术的组织里，把 AI 真正用起来。

西藏课题
课题组十余人长期用 Excel 手工处理每季度几千份问卷。我没有一开始就提议"大家改用 AI"，而是自己先用大模型做开放题文本的主题聚类与观点抽取，跑出结果、和人工编码结果做对比，确认可用之后才拿给导师看。导师认可后再推广到全组——先自证，再推广。开放题分析效率提升约 3 倍。
极米科技
在海外 GTM 岗位上，独立用飞书多维表格搭建覆盖区域 / 产品 / 渠道的周会看板，整合 Amazon 销售、供应链库存、售后 RMA、广告投放多源数据，配置定时自动拉取与跨源一致性校验；并基于实习中的真实痛点自行发起了第 07 项竞品分析 Agent 的设计。
共同点
都不靠"技术很先进"说服人，靠的是先把一个具体环节的结果做出来，再谈推广。
